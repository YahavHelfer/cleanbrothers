# Homepage service card images

Manage images at `/admin/pages/home`, in **שירותים**, under each service's **תמונות השירות בעמוד הבית** field. Select immutable versions from the existing media library, edit alt text/cropping, add, replace, remove (including the last image), and move images up or down. Uploads and file replacements remain in `/admin/media`, with existing validation and permissions. After uploading, save the open home draft and reload it to refresh the choices.

Save a draft, preview it, then publish the saved home revision. Service detail images remain independent. Published home reads use the existing `CMS_HOME_SOURCE=published` / `CMS_HOME_ALLOWLIST=home` gates and a request-memoized, uncached published-only RPC. The home action already revalidates `/` after publication.

For Production, first deploy the compatibility release (`605fabe`), which accepts and preserves both legacy cards and cards with image fields while retaining the previous renderer/editor. The original app rejects the new fields, and the final app requires their media references, so neither can safely straddle the migration alone. After confirming that compatibility release is READY on the Production domain and a current backup has been restored successfully, apply `20261003200000_cms_home_service_images.sql` through the linked cloud workdir; then deploy this final code with the CMS homepage source enabled. If the final application deployment fails, retain the compatibility release and expanded schema; do not delete revisions or roll back the schema. It seeds missing image fields using the exact previous card images/order/crops, imports the existing AC media if necessary, creates immutable successors for current draft/published home revisions, and preserves unpublished edits, explicit image lists (including empty lists), editor text, and historical revisions. The operator records migrated published successors as baseline events, with the previous revision retained through `base_revision_id`; it does not fabricate an editor publication or publish an unpublished draft. Both migration helpers use `CREATE OR REPLACE`, so directly rerunning the file is safe. Historical revisions are normalized when restored. New baseline imports use the same fields and verify all referenced static image hashes.

Image versions are pinned through the existing revision media references, so local/Supabase/S3 delivery, media usage reporting, archive rules, and environment scope guards continue to apply. Scope guards are disabled only inside the migration transaction while copying preexisting references and adding reviewed static references, then restored before commit; normal CMS permissions are unchanged.

The existing carousel handles keyboard, swipe, autoplay and reduced motion. It hides controls with one image. Empty cards use its styled fallback; the window card retains its existing illustration when empty and shows a carousel when editors select images.

Validation: `npm test`, `npm run lint`, `npx tsc --noEmit`, `npx next build --webpack`; database coverage is in `supabase/tests/database/cms_home_service_images.test.sql`, and refresh/publication/desktop/mobile browser coverage is in `tests/e2e/cms-homepage.spec.ts`. The latter two require the dedicated local Supabase/Docker stack.
