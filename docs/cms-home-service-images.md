# Homepage service card images

The later shared-image extension and its local verification/deployment instructions are documented in [cms-shared-service-images.md](cms-shared-service-images.md). The production evidence below describes the earlier homepage-only release.

Manage images at `/admin/pages/home`, in **שירותים**, under each service's **תמונות השירות בעמוד הבית** field. Select immutable versions from the existing media library, edit alt text/cropping, add, replace, remove (including the last image), and move images up or down. Uploads and file replacements remain in `/admin/media`, with existing validation and permissions. After uploading, save the open home draft and reload it to refresh the choices.

Save a draft, preview it, then publish the saved home revision. Service detail images remain independent. Published home reads use the existing `CMS_HOME_SOURCE=published` / `CMS_HOME_ALLOWLIST=home` gates and a request-memoized, uncached published-only RPC. The home action already revalidates `/` after publication.

Before migrating another environment, deploy an expansion release that accepts/preserves both legacy cards and image fields, recognizes `home-service:*` media roles, and explicitly copies only `title`, `benefit`, and `description` into the old renderer. Spreading a migrated card into the old service object passes image objects to a carousel expecting strings. Confirm the expansion release on the live domain and restore-test a current database backup before applying `20261003200000_cms_home_service_images.sql`; then deploy the final renderer/editor. **Do not use `605fabe` or the original `1216bca` as a rollback against the migrated database with the CMS homepage enabled.** For a rendering rollback, follow `docs/cms-production-handover.md`: disable only `CMS_HOME_SOURCE` and redeploy the known-good code to use the static homepage. Preserve the expanded schema and immutable revisions; do not delete content or apply a destructive down migration. It seeds missing image fields using the exact previous card images/order/crops, imports the existing AC media if necessary, creates immutable successors for current draft/published home revisions, and preserves unpublished edits, explicit image lists (including empty lists), editor text, and historical revisions. The operator records migrated published successors as baseline events, with the previous revision retained through `base_revision_id`; it does not fabricate an editor publication or publish an unpublished draft. Both migration helpers use `CREATE OR REPLACE`, so directly rerunning the file is safe. Historical revisions are normalized when restored. New baseline imports use the same fields and verify all referenced static image hashes.

Image versions are pinned through the existing revision media references, so local/Supabase/S3 delivery, media usage reporting, archive rules, and environment scope guards continue to apply. Scope guards are disabled only inside the migration transaction while copying preexisting references and adding reviewed static references, then restored before commit; normal CMS permissions are unchanged.

The existing carousel handles keyboard, swipe, autoplay and reduced motion. It hides controls with one image. Empty cards use its styled fallback; the window card retains its existing illustration when empty and shows a carousel when editors select images.

Validation: `npm test`, `npm run lint`, `npx tsc --noEmit`, `npx next build --webpack`; database coverage is in `supabase/tests/database/cms_home_service_images.test.sql`, and refresh/publication/desktop/mobile browser coverage is in `tests/e2e/cms-homepage.spec.ts`. The latter two require the dedicated local Supabase/Docker stack.
