# CMS media object storage authorization spike (local only)

Status: architecture proposal and mock-only prototype. No provider is connected to a route, no bucket or credentials exist for this spike, and no Supabase migration is prepared or applied. Cloud migration #23 and the existing Supabase Canary are untouched.

## Finding and recommendation

Keep Supabase Auth, AAL2 membership, `media_assets`, immutable `media_versions`, `revision_media_refs`, and current-publication authorization. Move only newly uploaded object bytes to a private, dedicated store. Preserve static and legacy Supabase providers by dispatching on each registered version's provider; never rewrite historical rows as a side effect of reading.

**For the strict requirement that even the application's long-lived credential cannot list, prefer AWS S3 with an object-ARN-only IAM policy and no `s3:ListBucket` grant.** A Vercel-to-AWS OIDC role is worth evaluating before issuing a static access key. R2 remains an attractive cost/compatibility candidate, but its ordinary bucket-scoped Object Read & Write parent token *includes listing*. Locally signed R2 temporary credentials can narrow a request to `GetObject`, `HeadObject`, `PutObject`, and `DeleteObject` on one exact object and exclude `ListObjectsV1/V2`; the parent token still has bucket-wide read/write/list authority. R2 is acceptable only if that parent-token blast radius, or the cost of a separate trusted credential broker, is approved explicitly. This is not a proof of live R2 behavior: no account, bucket, or live API request was made. [R2 token permissions](https://developers.cloudflare.com/r2/api/tokens/), [R2 temporary credentials](https://developers.cloudflare.com/r2/api/s3/temporary-credentials/), [AWS S3 permissions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-with-s3-policy-actions.html), [Vercel AWS OIDC](https://vercel.com/docs/oidc/aws).

| Candidate | Exact GET without list | Credential exposure | Operations, cost and integration |
| --- | --- | --- | --- |
| Cloudflare R2 | Yes with **locally signed** temporary credentials using explicit `actions` and `paths.objectPaths`; not with its ordinary parent bucket token | Temporary exact-object credential is short-lived; parent token can list/read/write that bucket and must remain in a trusted server or separate broker | S3-compatible from a Vercel Node function. Separate R2 account/bucket and token lifecycle. R2 bills storage/operations and advertises no R2 egress charge; Vercel function/CDN transfer is a separate cost. |
| AWS S3 | Yes: grant `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject` on object ARNs only; omit `s3:ListBucket` | IAM role/key can be limited to one bucket prefix and object operations; short-lived OIDC credentials can avoid a static key in Vercel | Mature SDK/IAM, but AWS role/bucket policy and region management add setup. Storage, requests and outbound transfer pricing depend on region and usage. |
| Supabase Storage with elevated server secret | The server can avoid calling list, but the elevated credential is not a provider-level no-list boundary | Supabase secret/service-role-class authority is much broader than the media bucket and bypasses user RLS | Easiest legacy integration, but conflicts with the least-privilege and no-privileged-Supabase-key requirements. Not recommended. |

R2's action-scoped temporary credential feature is currently documented for **local signing only**, not its Temporary Credentials API. Broad presets such as `object-read-only` include list. R2 private buckets are private by default, and `PutObject` supports `If-None-Match` for atomic no-overwrite uploads. [R2 temporary credentials](https://developers.cloudflare.com/r2/api/s3/temporary-credentials/), [R2 private buckets](https://developers.cloudflare.com/r2/buckets/public-buckets/), [R2 S3 compatibility](https://developers.cloudflare.com/r2/api/s3/api/), [R2 pricing](https://developers.cloudflare.com/r2/pricing/), [AWS S3 pricing](https://aws.amazon.com/s3/pricing/).

An object-only credential still permits GET or deletion of a *known* key within its grant. UUID secrecy is not authorization. Restrict the key's bucket/prefix, split read and mutation roles where practical, keep credentials out of browser bundles and logs, and make the application routes perform their own CMS authorization before issuing any object request. The no-overwrite rule protects ordinary application writes; a stolen write/delete credential could still damage historical objects. Provider-enforced write-once retention is a separate decision, and R2's S3 compatibility currently marks object locking unsupported. Without `ListBucket`, S3 may answer `403` for a missing key rather than `404`; map both to the same fail-closed route response. [R2 S3 compatibility](https://developers.cloudflare.com/r2/api/s3/api/), [S3 HEAD permission and missing-key behavior](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html).

## Prototype boundary

`src/cms/media/object-store.ts` defines the server-only `MediaObjectStore` interface with exactly `putExact`, `headExact`, `getExact`, and `deleteExact`. Every call takes a version UUID and derives `cms-media/<versionId>.webp` internally. No object-store list or caller-supplied path exists; the CMS library may still list *authorized database metadata*. The backend interface is an adapter seam, not a credential provider. Its `putIfAbsent` must be atomic; a future S3/R2 adapter must use a conditional put, not a HEAD-then-PUT race. `readAuthorizedExact` accepts only an authorized version record and verifies byte length and SHA-256 before returning bytes. Neither the interface nor the mock is wired into existing routes yet.

The local mock tests prove UUID/path rejection, absence of a list method, exact-key calls, no overwrite of an existing version, independent exact objects for new versions, hash/size failure, and compensation confined to a newly created key. Its authorization callbacks model two AAL2 admins reading the same historical version and an unauthorised public read being rejected before object access. This is a **boundary contract test**, not a real CMS AAL2, S3, or R2 integration test. Existing current-publication SQL/RLS tests remain the authority for public reference eligibility.

## Proposed runtime flows

1. **Admin read:** `/admin/media/file/[id]` calls existing `requireCmsAdmin()` (active membership and AAL2), reads the exact `media_versions` row through the Admin session, derives the key from the registered UUID, gets bytes server-side, verifies `byte_size` and SHA-256, and returns private/no-store/noindex bytes. Never expose storage URL or credential.
2. **Public read:** `/cms-media/[id]` calls the existing `cms_read_public_media_version` RPC and retains all current service/page/home/promotion source gates. Only a currently referenced, approved published version reaches the object store. Hash-check before returning bytes. Historical-only or unreferenced versions stay private.
3. **Upload:** existing protected upload route keeps exact Origin/Host, `requireCmsAdmin()`, image validation, WebP normalization, size limit and fresh UUID. Server conditionally puts `cms-media/<UUID>.webp`, then performs authenticated registration for that exact version. A definite registration rejection may delete only this newly put object; an ambiguous network result must leave a private orphan for reconciliation. Never delete a registered/historical version as compensation.
4. **Delete:** `deleteExact` is an internal orphan-compensation/explicit audited maintenance primitive only. Archive, remove from page, unpublish and rollback never delete historical bytes. A later cleanup process must prove no registered/current/historical reference before deletion; it must not infer orphanhood from a failed request or use bucket listing.

### Registration trust gap that must be resolved before rollout

The current authenticated Supabase registration RPC checks `storage.objects` for the Supabase upload. An R2/S3 object is outside that database; simply replacing its `storage_provider` constraint and keeping a user-callable RPC would let an AAL2 caller register a non-existent remote object. A future migration needs a server-to-database attestation bound to the actor, version UUID, object hash/size, metadata, target asset/generation and short expiry, with replay protection, or another comparably narrow server-only registration proof. The server must verify remote object existence/integrity before attesting. The attestation secret must be separate from the object-store credential, never browser-visible; the database must not receive an object-store credential. This is a design requirement, not an implemented change.

## Schema and compatibility proposal

A **future, separately reviewed migration** would add `s3` to the `media_versions.storage_provider` and location constraint, with a fixed private bucket identifier and `storage_path = 'cms-media/' || id::text || '.webp'`. It would add a dedicated authenticated registration RPC with the proof above and retain immutable version/reference constraints. Public/Editor projection validators and typed TypeScript provider unions would need the new value. Existing rows stay `static`, `local`, or `supabase`; the legacy `cms-media-preview` and `cms-media-production` read paths stay available under their current gates until each historical object is audited and migrated under a separate decision. Do not rewrite old rows, repoint an existing version, or remove the Canary. The current Supabase private-read problem remains for legacy objects until separately resolved.

No current DB schema or migration changed during this spike. The next number is not reserved here; any future migration requires a fresh dry-run and explicit cloud approval.

## Rollout proposal, not authorization

1. Choose provider after an explicit decision on parent-credential listing risk, cost and account ownership. Create a dedicated private bucket and narrow identity in a separate approved phase; for R2, disable both public `r2.dev` and custom-domain access. Keep Preview and Production credentials separate.
2. Implement one real server-only S3-compatible adapter and the registration attestation; test conditional no-overwrite, GET/HEAD/PUT/DELETE grants, denied list, missing-key behavior, credential leakage, and historical/public authorization against an isolated non-production bucket.
3. Add the narrowly reviewed schema/RPC migration locally, then cloud dry-run. Keep new upload writes gated off by default; preserve static and legacy provider reads.
4. Enable one protected Preview upload, Draft, Exact Preview, Publish, historical-version, rollback and orphan test. Verify current-reference public delivery and private/anonymous denial. Reconcile orphans by known version IDs from an audited DB workflow, not `ListObjects`.
5. Only after Preview proof and separate approval, deploy Production code with new uploads still off, then enable the exact new-upload gate. Keep the Supabase Canary and old media untouched until a dedicated migration plan is approved.

Nothing in this document authorizes cloud mutations, provider account creation, a public bucket, secrets, Production flags or a commit.
