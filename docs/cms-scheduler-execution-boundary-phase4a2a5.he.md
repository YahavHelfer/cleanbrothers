# Phase 4A2-A5 — גבול ביצוע למתזמן מבצעים

המיגרציה `20260928120000_cms_scheduler_execution_boundary.sql` היא מקומית בלבד בשלב זה. היא משנה את שם מנוע הביצוע הקיים ל־`public.cms_process_due_promotion_schedules_at(timestamptz, integer)` בלי לשנות את אלגוריתם הנעילה, המעברים, הניסיונות החוזרים או ה־audit. פונקציה זו מקבלת זמן מפורש ומשמשת רק בדיקות ומפעיל DB מבוקר. הרשאת `EXECUTE` שלה נשללת מ־`PUBLIC`, מ־`anon`, מ־`authenticated` ומ־`service_role`; בעל הפונקציה הוא `postgres`.

מעטפת הייצור `public.cms_process_due_promotion_schedules(integer default 100)` אינה מקבלת זמן. היא דוגמת פעם אחת את `pg_catalog.clock_timestamp()` בעת הכניסה לפונקציה ומעבירה את הערך היחיד לליבה. זהו שעון הקיר של שרת PostgreSQL בזמן הקריאה, בשונה מ־`now()` הקבוע לתחילת הטרנזקציה. כל המעברים והחותמות באותה ריצה משתמשים באותה דגימה. גם המעטפת היא `SECURITY DEFINER` בבעלות `postgres`, עם `search_path` ריק ושמות פונקציות מוכשרים בסכמה. כך תפקיד המתזמן העתידי יוכל לקבל רק `EXECUTE` על המעטפת, בלי גישה ישירה לטבלאות הכפופות ל־forced RLS או לליבה עם זמן מפורש. בשלב זה המעטפת אינה מוענקת לשום תפקיד מכונה; `PUBLIC`,‏ `anon`,‏ `authenticated` ו־`service_role` אינם רשאים להריץ אותה. בעלות `postgres` היא הרשאה רחבה *בתוך* הפונקציות, ולכן נדרשת בדיקת diff מוקפדת לכל שינוי עתידי בגופן; אין כאן הרשאה כללית למזמן.

בפיילוט הענן הידני העתידי, מפעיל DB מורשה יתחבר ישירות לפרויקט ה־CMS ויזמן את הליבה עם timestamps מדומים, לאחר אישור נפרד. אין נתיב HTTP, Server Action, עמוד Admin או מפתח Vercel לגישה לזמן המדומה. תפקיד ה־Cron העתידי לא יקבל `EXECUTE` על הליבה.

`pg_cron` הוא מועמד בלבד. לפני התקנה או job יש להוכיח בסביבת Supabase המתארחת שתפקיד `LOGIN` ייעודי יכול להריץ את ה־job עם `EXECUTE` על המעטפת בלבד, ללא `BYPASSRLS`, ללא `service_role`, ללא הרשאות DML לטבלאות וללא סוד רחב מחוץ ל־Postgres. יש לאמת גם את שיטת האימות של חיבור ה־job, את הבעלות על ה־job, ואת האפשרות למנוע מהתפקיד יצירת jobs שרירותיים לאחר provisioning. אין fallback שקט ל־job בבעלות `postgres`. אם התנאים הללו אינם מתקיימים, תכנון `pg_cron` אינו מאושר ויש לבחור גבול ביצוע אחר.

המיגרציה אינה מתקינה הרחבה, אינה יוצרת תפקיד ענן, אינה יוצרת job, אינה מוסיפה secret או משתנה סביבה, ואינה מפעילה את המתזמן בענן. שירותי האתר, Production ו־CRM אינם משתנים. ביטול עתידי של תשתית מתזמן יתחיל בהשבתת ה־job ובהסרת ההרשאה למעטפת; הנתונים וה־audit נשמרים.
