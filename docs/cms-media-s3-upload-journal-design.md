# CMS media on S3 — final local registration and upload-journal design

Status: **local design and rollback-only proof; not a migration or deployed implementation**. This supersedes the nonce-ledger and existing-asset-only proposal in the [earlier attestation spike](cms-media-s3-registration-attestation-spike.md). No AWS, hosted Supabase, Vercel, Production, CMS content, or Canary state was changed.

## Trust boundary and transaction

The server requires `requireCmsAdmin()` and an active AAL2 membership, validates and normalizes a WebP (1–4 MiB, dimensions at most 6000×6000 and 16 million pixels), and computes SHA-256. The authenticated `prepare` RPC independently checks AAL2/membership, validates the exact metadata, binds `actor_id=auth.uid()`, generates UUIDv4 in Postgres, derives `cms-media/{version_id}.webp`, and inserts a `prepared` journal row. Neither a browser-chosen UUID/key nor direct `INSERT`/`UPDATE`/`DELETE` on the journal is granted. A browser with the same CMS session could call the *narrow prepare RPC* and create a valid-looking prepared row, but cannot choose identity/status or register it without the server-only HMAC key. Rate-limit the upload endpoint and age-monitor `prepared` rows to limit clutter.

The server conditionally `PutObject` with `If-None-Match: *`, then checks the exact object with `HeadObject` for length, WebP type, version metadata, and SHA-256 metadata. It marks the row `uploaded` through a narrow RPC, signs the fixed [canonical attestation](../src/cms/media/s3-registration-attestation.ts), and invokes registration with the same authenticated CMS session. This is a server assertion of the checked S3 response; Postgres does not hold AWS credentials or independently read S3. Head metadata is not a cryptographic proof of bytes, so Admin/public delivery still GETs bounded bytes and verifies the registered length and SHA-256 before returning anything. A real upload can additionally GET/hash immediately after PUT if required by the threat model.

The registration RPC takes `version_id`, `target_asset_id`, `expected_generation`, `details`, `metadata`, the signed payload and signature. It checks exact equality among ordinary RPC arguments, all signed fields, and the locked journal row; `object_key` is also re-derived. The signed payload binds `keyId`, actor, version UUID, target/null, generation/null, `s3`, key, byte size, dimensions, WebP MIME, hash, original filename, editable metadata, issued/expiry seconds and a 128-bit nonce. It rejects unknown fields, malformed types, expired signatures (DB clock, max 60 seconds, at most 5 seconds future skew), wrong actor, AAL1/nonmembers, and invalid HMAC. Use a fixed empty `search_path`, schema-qualified relations/functions, explicit `REVOKE` from `PUBLIC`/`anon`/`service_role`, and exact `EXECUTE` grants to `authenticated`. The result is a single database transaction, with the journal row selected `FOR UPDATE`.

For **new asset** (`target_asset_id` and generation both NULL): create an `available` `media_assets` row with a database-generated asset UUID and generation 1, create immutable `media_versions` version 1 with the prepared UUID and exact S3 key, set `current_version_id`, insert an `upload` audit event, then mark the journal row `registered` and link `registered_media_version_id=version_id`. Any error rolls back all five effects. The real future migration must extend existing `media_versions` provider/location checks for `s3` without altering static/local/Supabase historical rows.

For **replacement**: lock the target `media_assets` row, require `available` and exact generation, compute `max(version_number)+1` under that asset lock, insert an immutable version, move only the current pointer, increment generation, update approved display metadata, insert a `replace` audit event, and mark the journal row `registered`. Old versions and their historical references remain untouched. A stale generation returns a conflict and leaves the attempt `uploaded` for a separate definite-failure decision.

## Journal schema and state machine

The proposed `public.cms_media_upload_attempts` fields are:

| Field | Constraint / purpose |
| --- | --- |
| `version_id uuid primary key` | Generated by prepare; never reused or removed while object/history may exist. |
| `actor_id uuid not null` | `auth.uid()` at preparation, not an RPC argument. |
| `target_asset_id uuid null`, `expected_generation bigint null` | Both NULL for new asset, both set for replacement; generation positive. |
| `provider text not null`, `object_key text not null unique` | Exactly `s3`; key CHECK equals `cms-media/` + version UUID + `.webp`. |
| `byte_size`, `width`, `height`, `mime_type`, `content_hash`, `original_filename` | Exact validated normalized upload identity; WebP only, SHA-256 lowercase 64 hex, bounded size/pixels/filename. |
| `alt_text`, `caption`, `folder` | Same validated values bound into the attestation and eventual asset row. |
| `status text not null`, `created_at`, `updated_at` | Status CHECK/transition trigger; indexed `(status,updated_at,version_id)` for reconciliation. |
| `registered_media_version_id uuid null` | FK to immutable version; non-NULL iff `registered`, and equals `version_id`. |
| `last_error_code text null` | Closed enum of sanitized operational codes for terminal failures; never raw S3/SQL error text. |

Six durable states suffice: `prepared → uploaded → registered`; `prepared/uploaded → ambiguous`; `prepared/uploaded → definite_failure → cleaned`; and `ambiguous → registered` after exact-object verification and fresh signing. `ambiguous → definite_failure` is **operator reconciliation only** after locking the row, proving no version committed, and terminalizing it so any late registration must fail. `registered` and `cleaned` are terminal. `registering` is omitted: registration is an atomic SQL transaction, so no external observer can see a durable intermediate registering state. A trigger rejects unapproved transitions and changes to identity/metadata fields; RLS is enabled and forced, with no direct journal writes for browser roles.

The DB constraints additionally require provider `s3`, WebP MIME, positive dimensions/size, pixel limit, SHA-256 format, exact key, paired target/generation NULLs, registered-link consistency, unique `(asset_id,version_number)` and unique `(provider,object_key)` in `media_versions`. The real migration must use the existing media FK, immutable-version trigger, audit immutability and AAL2 membership guard. No journal field is a public URL or AWS credential.

## Failure, replay, cleanup and reconciliation

`version_id` uniqueness, a retained journal row, its `FOR UPDATE` lock, and the immutable version PK are the one-use guard. **No second nonce ledger is required.** The random nonce remains in the signed payload for signature uniqueness, but replay of a successful registration finds `registered` and fails; two concurrent registrations serialize on the same journal row. A failed transaction rolls back its journal/version/asset/audit changes together, allowing a fresh short-lived attestation for the same uploaded object. The earlier nonce-ledger prototype remains a historical proof, not the final design.

| Observation | Durable action | Object action |
| --- | --- | --- |
| Definite Put rejection that guarantees no write | `definite_failure` with `PUT_REJECTED` | No delete needed. A 412 key collision or transport timeout is **ambiguous**, not this case. |
| Put and exact Head succeed | `uploaded` | Keep exact object. |
| Registration succeeds | `registered` atomically with asset/version/audit | Keep permanently for immutable history. |
| Deterministic registration rejection is received and no version committed | Lock/terminalize as `definite_failure` | Delete only exact key; mark `cleaned` only after a confirmed 2xx DeleteObject. |
| DB/S3 timeout, lost response, 403/404 ambiguity, or unknown in-flight result | `ambiguous` or leave `uploaded` if even status update is unavailable | **Do not delete.** Reconcile later. |

Cleanup eligibility is the conjunction of: exact known `version_id`; journal key equals the key derived from it; terminal `definite_failure`; no `media_versions` row for that UUID; and definite knowledge that registration cannot still commit. Terminalization under the journal lock makes late registration reject. A successful exact DeleteObject must be attested by the trusted server before marking `cleaned`; a browser must not be able to mark a row cleaned merely by claiming it deleted bytes. A dedicated, domain-separated short-lived HMAC cleanup receipt (version, actor, completed time, nonce, action=`delete-exact`) is the narrow recommended boundary. If DeleteObject's outcome is ambiguous, retain `definite_failure` and retry/reconcile; never claim `cleaned`. A journal row is retained after cleanup, preventing UUID/key reuse. In-flight or ambiguous Put must remain quarantined until the worker outcome is known; elapsed time or `HeadObject` 403 alone is not deletion proof.

Reconciliation queries only the journal index for `uploaded` not registered, `ambiguous`, `definite_failure` not cleaned, `registered`, and `cleaned`. An AAL2 operator can read sanitized rows; the server uses only `headExact`/`getExact`/`deleteExact` for **those known UUIDs**. For uploaded/ambiguous rows, compare the locked DB version status and exact S3 length/type/hash metadata; if needed GET and hash, then sign a fresh attestation and register, or explicitly terminalize after a confirmed no-commit outcome. A `403` on HEAD without `ListBucket` is unresolved, not proof of absence. Registered rows are read-only; cleaned rows remain as durable tombstones. No bucket listing, guessed keys, bulk delete, or automatic cleanup of historical media.

## Minimum RPC surface (future migration, not applied)

The concrete names below are design signatures, not deployed functions:

```sql
public.cms_prepare_external_media_upload(
  target_asset uuid, expected_generation bigint,
  byte_size integer, width integer, height integer,
  content_hash text, original_filename text, metadata jsonb
) returns uuid;

public.cms_mark_external_media_uploaded(version_id uuid) returns void;

public.cms_register_external_media_version(
  version_id uuid, target_asset uuid, expected_generation bigint,
  details jsonb, metadata jsonb,
  attestation jsonb, signature text
) returns uuid;

public.cms_mark_external_media_ambiguous(version_id uuid) returns void;
public.cms_mark_external_media_definite_failure(
  version_id uuid, reason_code text
) returns void;
public.cms_complete_external_media_cleanup(
  version_id uuid, cleanup_receipt jsonb, signature text
) returns void;
public.cms_read_external_media_attempts(status_filter text default null)
  returns setof public.cms_media_upload_attempts;
```

All writes are narrow `SECURITY DEFINER` functions with fixed search path, independent AAL2/member checks and row locking. `mark_uploaded` cannot register anything without the HMAC; `mark_definite_failure` accepts only code-owned reason codes and must prove no registered version. `complete_cleanup` validates the distinct signed delete receipt and prior eligible terminal state. Read RPC returns only sanitized journal fields to AAL2 admins; raw HMAC material, AWS response, cookies and storage URLs are excluded. There is no generic set-status RPC or direct table-write grant. The local SQL surrogate proves the core data transaction and state guards; it does not yet implement the cleanup receipt or actual S3 outcome verification.

## HMAC key storage and exact-object adapter

Use one random dedicated registration/cleanup HMAC key per environment, with `keyId` rotation. Keep the signing copy only in server-only Vercel environment storage, never `NEXT_PUBLIC_*`; the DB verification copy should be provisioned outside migration through **Supabase Vault**, if confirmed available on the dedicated CMS project. Store it under a fixed, non-caller-controlled name/id, restrict `vault.decrypted_secrets`/secret-management access, and retrieve it only in the fixed `SECURITY DEFINER` verifier. Vault encrypts secrets at rest but its decrypted view is sensitive; DB owner/privileged operator access remains a real trust boundary. Do not put plaintext in source-controlled SQL, a broad session GUC, a browser bundle, an AWS key, a Supabase publishable/service key or `CMS_MEDIA_SERVER_KEY`. If Vault or equivalent controlled secret facility is unavailable on the hosted project, stop for a separate review rather than silently falling back to a plaintext table. [Supabase Vault](https://supabase.com/docs/guides/database/vault), [function hardening](https://supabase.com/docs/guides/database/functions).

The server-only [`MediaObjectStore`](../src/cms/media/object-store.ts) now exposes exactly `putExact(versionId, bytes)`, `headExact(versionId)`, `getExact(versionId)`, and `deleteExact(versionId)`. All derive their key internally. The injected S3 adapter has exact Put/Head/Get/Delete only, no list or arbitrary-key public API. Put is conditional, followed by Head verification. `headExact` returns bounded, validated length/type/version/hash metadata; network/403/unknown errors propagate rather than being converted into absence. S3 documents that `HeadObject` needs `GetObject` and a missing key can produce `403` without `ListBucket`. [AWS HeadObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html), [conditional write enforcement](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes-enforce.html).

## Local proof and remaining rollout work

[`cms_s3_upload_journal_local.sql`](../supabase/spikes/cms_s3_upload_journal_local.sql) creates only a surrogate schema and synthetic users inside one transaction, exercises new-asset and replacement registration, AAL1/nonmember/wrong-actor denial, signed expiry, argument and attestation mismatches, missing journal, signed generation conflict, replay, ambiguous cleanup denial, definite-failure cleanup eligibility, no direct journal write grants and atomic audit/version/pointer results, then ends `ROLLBACK`. It intentionally does **not** create a migration, register a real S3 object, or alter existing media rows. The previous mock tests continue to prove cross-admin historical reads at the authorization callback boundary and absence of a list method.

A future separately approved implementation must adapt the real `media_versions` constraints/projections/routes, add the Vault verifier and cleanup receipt, implement an AWS SDK exact client and IAM/OIDC setup, add operational reconciliation, and test against hosted Supabase/S3 before enabling any source. The Supabase private Storage Canary and migration #24 are untouched.
