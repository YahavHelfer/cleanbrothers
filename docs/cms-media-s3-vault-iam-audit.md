# CMS S3 media — Vault capability and IAM boundary audit

Status: **historical read-only CMS cloud catalog audit and local IAM proposal, 2026-10-02**. The implemented S3 Preview flow uses a dedicated hash-checked server capability and does **not** use Vault or HMAC. The Vault designs below remain unimplemented audit findings. The audit targeted only Supabase project `plbwefnwussxlglscfpn` using `supabase db query --linked --project-ref`. Queries selected extension/catalog metadata and effective privileges; none selected Vault rows, decrypted values, secret names or plaintext. No AWS identity, bucket, key, Vault secret, grant, SQL function, migration or deployment was created by this audit.

The direct-client boundary is **supported**: `authenticated` cannot use the Vault schema or SELECT its decrypted view. `authenticator` has no *direct* Vault privilege, but can `SET ROLE service_role` through its existing PostgreSQL membership; this is another reason the service-role grants matter. `postgres` has the required privileges and `CREATEROLE`. It also has grant option for Vault view/schema USAGE and owns `extensions`, so a dedicated NOLOGIN verifier-owner role appears technically feasible. The view has no `security_invoker` option, but its decrypt function runs with invoker rights; the dedicated owner would need Vault schema USAGE, view SELECT and decrypt-function EXECUTE, plus `extensions` USAGE for `hmac`. No role/function was created to prove the path live. [PostgreSQL view permissions](https://www.postgresql.org/docs/17/sql-createview.html), [Supabase Vault](https://supabase.com/docs/guides/database/vault).

The stronger statement **“only the narrow registration verifier can read the secret” is not true under current grants**: `service_role` has explicit SELECT on both Vault relations, Vault schema USAGE, and EXECUTE on the decrypt and secret-management functions. Revoking SELECT on `vault.decrypted_secrets` **alone is insufficient**: the encrypted table and invoker decrypt function remain callable, and secret-management EXECUTE remains. `postgres` and `supabase_admin` remain privileged operators by design. The S3 media architecture does not use or provision a `service_role` credential, but a separately compromised existing service-role credential or direct DB session with that role could read a future Vault verifier secret. The Vault schema's Data API exposure was not audited here, so the catalog result establishes database privilege, not a demonstrated HTTP route. Do **not** claim strict verifier-only isolation or provision the HMAC secret yet; no grant was changed in this audit.

## Privilege-hardening feasibility (read-only, 2026-10-02)

The role map also confirms that `anon`, `authenticated`, `authenticator` and `cms_scheduler` have no direct Vault schema USAGE, relation SELECT or Vault-function EXECUTE. `authenticator` has `SET ROLE` but not inheritance for its `service_role` membership; `postgres` inherits its service-role membership and remains a privileged administrator. On `extensions.hmac(bytea,bytea,text)`, EXECUTE is currently granted to PUBLIC, but use still requires `extensions` schema USAGE. No extra HMAC EXECUTE grant is needed for a verifier role under current ACLs, though an explicit grant could make its dependency clear. None of these observations involved reading a Vault row or secret name.

**Option A:** Revoking only `service_role` SELECT on `vault.decrypted_secrets` is syntactically feasible but does not establish the desired boundary. A strict future proposal would also remove `service_role` SELECT/DELETE on `vault.secrets`, DELETE on the view, EXECUTE on `vault._crypto_aead_det_decrypt(bytea,bytea,bigint,bytea,bytea)`, `vault.create_secret(text,text,text,uuid)` and `vault.update_secret(uuid,text,text,text,uuid)`, and USAGE on schema `vault`. Keep `postgres`/`supabase_admin` administrative privileges and the existing `authenticated` denial. There is no identified **CMS/database** dependency on decrypted-view SELECT, but the Vault objects are members of the Supabase-managed `supabase_vault` extension and platform/internal use or upgrade re-grants have not been excluded. Treat the revokes as a proposed, separately approved migration with a compatibility test and post-upgrade grant drift check, not safe to apply from this catalog scan alone.

**Option B (preferred conditional design):** Create a dedicated `NOLOGIN NOINHERIT NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE` role with no memberships. Grant it only `USAGE ON SCHEMA vault`, `SELECT ON vault.decrypted_secrets`, `EXECUTE ON FUNCTION vault._crypto_aead_det_decrypt(bytea,bytea,bigint,bytea,bytea)` and `USAGE ON SCHEMA extensions` (plus explicit `EXECUTE ON extensions.hmac(bytea,bytea,text)` if the existing PUBLIC grant is later removed). Do not grant it direct `vault.secrets` table or Vault secret-management privileges. Own a single `SECURITY DEFINER` verifier in a private, non-API schema with this role; grant schema USAGE and function EXECUTE only to the trusted `postgres`-owned registration RPC path, not to `authenticated`, `anon`, `service_role` or PUBLIC. The outer registration RPC separately enforces active membership, AAL2, journal state, exact version ID and replay checks. Creating the private function and revoking its default PUBLIC EXECUTE must be atomic. The verifier uses a fixed secret name, `SET search_path = ''` with schema-qualified objects, canonical HMAC input and a reviewed comparison mechanism, and returns only a Boolean. No caller-supplied secret identifier, generic secret accessor, secret-bearing error or log is allowed. Because view SELECT is relation-wide, the role's **function code** is what narrows lookup to one secret; `NOLOGIN` does not prevent an improperly granted function from leaking secrets. This design still requires Option A's broader service-role cleanup to make a verifier-only claim. [PostgreSQL SECURITY DEFINER guidance](https://www.postgresql.org/docs/17/sql-createfunction.html), [PostgreSQL view permissions](https://www.postgresql.org/docs/17/sql-createview.html).

The following are **proposed privilege statements only; do not execute without a separate compatibility proof and approval**. The private schema/function and outer RPC would be separately reviewed; the latter alone would be callable by `authenticated` and would retain all AAL2/journal checks.

```sql
-- Existing service-role grants to remove for a strict verifier-only boundary.
REVOKE SELECT, DELETE ON vault.decrypted_secrets FROM service_role;
REVOKE SELECT, DELETE ON vault.secrets FROM service_role;
REVOKE EXECUTE ON FUNCTION vault._crypto_aead_det_decrypt(bytea, bytea, bigint, bytea, bytea) FROM service_role;
REVOKE EXECUTE ON FUNCTION vault.create_secret(text, text, text, uuid) FROM service_role;
REVOKE EXECUTE ON FUNCTION vault.update_secret(uuid, text, text, text, uuid) FROM service_role;
REVOKE USAGE ON SCHEMA vault FROM service_role;

-- After creating a dedicated NOLOGIN verifier-owner role with no memberships.
GRANT USAGE ON SCHEMA vault TO cms_media_vault_verifier;
GRANT SELECT ON vault.decrypted_secrets TO cms_media_vault_verifier;
GRANT EXECUTE ON FUNCTION vault._crypto_aead_det_decrypt(bytea, bytea, bigint, bytea, bytea) TO cms_media_vault_verifier;
GRANT USAGE ON SCHEMA extensions TO cms_media_vault_verifier;
-- extensions.hmac(bytea,bytea,text) currently already grants EXECUTE to PUBLIC.
```

The future private verifier function's default PUBLIC EXECUTE would be revoked in the same transaction as creation, then EXECUTE and private-schema USAGE granted only to the trusted registration-RPC owner (`postgres`). No Vault privilege would be granted to the caller role. Whether Supabase's managed Vault extension tolerates removing every listed service-role privilege, and whether a dedicated owner can run the view end-to-end, still require a separately authorized transactional/live proof. Recheck effective privileges, platform behavior and extension upgrades before storing a real HMAC secret.

The smallest later live proof, if this trust boundary is accepted or narrowed, is a separately authorized transaction with one random **test-only** Vault secret, a temporary fixed-name verifier that returns only a Boolean HMAC comparison, an AAL2/authenticated denial check, and a `ROLLBACK` plus residue check. It must never print the test value. The present catalog evidence proves installed APIs and effective grants, but not an end-to-end secret read through a newly created verifier. No live secret probe was performed.

Vault stores secret contents encrypted on disk and decrypts through the view at query time; Supabase says backups/replication retain the encrypted form, with the root key managed separately. A full schema/data export could include encrypted Vault table rows and metadata if included, whereas a deliberately executed decrypted-view SELECT or permissive `SECURITY DEFINER` function could leak plaintext. Provision the future secret outside source-controlled migrations and avoid SQL Editor drafts, literal-bearing logs, exception messages and RPC output. We did not run `pg_dump` or inspect any secret data. [Supabase Vault](https://supabase.com/docs/guides/database/vault).

## Proposed S3 IAM boundary (local document only)

The exact proposed JSON is [cms-media-s3-iam-policy.proposed.json](cms-media-s3-iam-policy.proposed.json). Replace `<DEDICATED_BUCKET>` only after separate AWS provisioning approval. Its sole Allow grants `s3:GetObject`, `s3:PutObject`, and `s3:DeleteObject` for object ARNs under `cms-media/*`; it has no bucket ARN Allow, `ListBucket`, `ListAllMyBuckets`, `GetBucketLocation`, ACL, policy, lifecycle, replication or wildcard Action Allow. S3 `HeadObject` uses `s3:GetObject`, so no separate HEAD IAM action is needed. [AWS S3 action mapping](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-with-s3-policy-actions.html), [HeadObject permissions and missing-key behavior](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html).

The explicit Deny applies to `ListBucket`, `ListBucketVersions`, `ListBucketMultipartUploads` and `ListAllMyBuckets` across `Resource: "*"`, preserving the no-list invariant if another Allow policy is attached later. AWS IAM states that an applicable explicit Deny overrides an Allow. This proposal does **not** itself prevent a later unrelated Allow from granting bucket administration or object access outside the prefix; the eventual role must remain dedicated, with attachment drift review or a permissions boundary if that stronger guarantee is required. No AWS policy simulator or account was used. [AWS IAM deny precedence](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_AccessPolicyLanguage_Interplay.html).

If this were the identity's only effective permission policy, leakage could read, put and delete **known** keys under the media prefix; it could not list buckets/objects or administer a bucket. A known UUID is not access control. DeleteObject on a known registered key can damage historical media; conditional Put is not immutable retention against a stolen Delete-capable credential. The server must generate UUIDv4, derive `cms-media/{versionId}.webp`, and send `PutObjectCommand` with `IfNoneMatch: "*"` to reject a current-key overwrite. The AWS SDK for JavaScript v3 command input includes `IfNoneMatch`, and S3 documents conditional writes. Bucket versioning/delete markers and stronger retention would need separate review. [AWS SDK v3 PutObjectCommand](https://github.com/aws/aws-sdk-js-v3/blob/main/clients/client-s3/src/commands/PutObjectCommand.ts), [AWS conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html).

Static JSON checks in this audit assert the expected three Allow actions, sole object-prefix Allow resource, four explicit Deny list actions, no wildcard Action, and no other statements. They do not replace an AWS policy simulation against a real identity. The application adapter remains the server-only exact-key Put/Head/Get/Delete prototype; no application runtime code changed.
