# Shared service images

## Behavior and editing

Manage images at **`/admin/pages/home` → שירותים → service → תמונות השירות**. The Hebrew help text explains that saving creates a private draft and publishing the homepage updates the homepage cards, `/services`, and that service's detail page together. The existing media library supports upload/replacement and the editor supports adding, replacing, removing, ordering, alt text, and approved crops.

All nine stable service slugs have independent collections. Services not currently represented by a homepage card still have image controls in the Services section. If that presentation section is removed, its image controls remain available independently. Detail-page editors link directly to the corresponding shared editor. Their former primary image and alt controls have been removed. Separate before/after, AC field-work gallery, and sharing images retain their editorial purpose and history.

The first image is the primary image where a display supports only one photo, including the window-cleaning hero and generic detail-page results photo. Existing carousels use the entire ordered collection and exact per-image alt text. One photo has no arrows/dots. An explicitly empty collection shows the existing generic placeholder or window illustration and never resurrects removed photos.

## Authoritative data and publication

`public.cms_service_image_collections` stores `(revision_id, service_key, images)`, with one immutable ordered collection per stable service slug for each homepage publication snapshot. Homepage blocks persist card copy only; their image arrays are read-time projections of this table. The listing and detail adapters read the same collections through the published homepage RPC, including services whose homepage block/card is hidden or absent. No application job synchronizes separate image copies.

All nine collections belong to one immutable homepage revision. The existing optimistic generation checks, private draft pointer, and atomic publication pointer govern both homepage copy and shared photography. Restoring home history creates a new private revision and restores the associated shared collections. Old service-primary fields remain in immutable service content/history for compatibility and preservation; public primary rendering and editable controls do not use them. Service copy is still published through its own editor.

Public readers share the published homepage snapshot within each request, call its anonymous published-only RPC with `cache: no-store`, and use request rendering when the homepage CMS source is enabled. Publishing revalidates `/`, `/services`, and all nine service detail paths, as well as the home editor. Private service previews combine their selected copy revision with the current shared homepage draft and label this explicitly. The media version upload/storage, AAL2, membership, scope, archive, immutable reference, and file-validation mechanisms remain in place. Direct API access to the collection table and helper functions is revoked.

## Migration

Prepared migration: `supabase/migrations/20261004100000_cms_shared_service_images.sql`, after `20261003200000_cms_home_service_images.sql`.

Precedence is: an existing canonical collection; otherwise an explicitly configured homepage image field (including `[]`); otherwise the corresponding legacy service's images; otherwise the approved static seed. Existing homepage selections always win, preserving their order, alt text, and crop. Published and draft legacy service pointers are read separately so an unconfigured service's unpublished images are not published during backfill.

The transaction creates immutable successors for current home pointers, without updating old revisions, blocks, media references, or editor-owned assets/versions. It retains service copy pointers and publication history. A single old home pointer is reused for both new pointers only when its published/draft collections agree; otherwise unpublished legacy service photography gets its own private home successor. Reapplying the migration skips fully configured current revisions and cannot overwrite subsequent editor changes. All three existing media scope triggers are restored before commit; failure rolls the entire migration back.

The migration's homepage projection preserves the existing card set, so the currently deployed homepage-image application can continue reading the migrated draft/public snapshots. The new ninth collection does not insert a ninth card into an older eight-card parser. The legacy save RPC remains available and derives collections from older submitted image fields while preserving collections for services not in that payload. New application saves use the authenticated shared-image RPC and persist only one canonical copy.
